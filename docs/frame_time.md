# Время кадра по частям, журнал без рывков, кеш конвейеров

Этап 5в, PR 2 (план — `docs/roadmap.md`, «Этап 5в»). Кадр GPU не меняется: этот шаг меряет, где процессор
тратит время кадра, и убирает ожидание диска из потока кадра.

## Откуда были рывки
Замер пользователя 7.11 (RTX 5070, без vsync): среднее 2.1–2.5 мс, а «макс» за секунду — 5.3–7.2 мс каждую
секунду, иногда 12. Наибольший кадр каждую секунду похожей длины — признак работы раз в секунду, а не случайной
помехи. Раз в секунду игра пишет журнал: заголовок, проходы GPU и хеши мира — 4 строки. Каждая строка шла в
файл через `SDL_FlushIO`, а это в SDL3 `FlushFileBuffers` на Windows и `fdatasync` на Linux — ожидание диска
прямо в потоке кадра. Плюс запись в консоль Windows (`.exe` консольный, журнал виден в терминале WSL).

Теперь строки журнала копируются в кольцо 256 КБ, а пишет их в stderr и файл свой поток (`platform_sdl.cpp`,
«Журнал»). Кадр не ждёт ни диска, ни консоли. Файл по-прежнему сбрасывается на диск после каждой пачки строк, но
уже потоком журнала. Ошибка (`log_error`) и аварийный выход (`ana_fail`) ждут, пока всё записано: последние строки
перед падением не теряются. При выходе `platform_shutdown` дописывает кольцо, закрывает файл и SDL (до `SDL_Quit`: после него
SDL не ждёт своих потоков, поэтому окно закрывает только видео и события).

Подтвердить, что рывки были от журнала, может только замер на машине пользователя (вкладка F3 «Кадр», ниже):
в контейнере диск и консоль другие.

## Части кадра
`FrameProf` (`src/core/prof.h`) — время каждой части кадра: среднее и наибольшее за секунду, из чего сложился
худший кадр секунды и полное время последних 256 кадров. Кадр — от начала итерации цикла до начала следующей,
поэтому сумма частей равна времени кадра. Части (`run_window.cpp`, `FramePartId`):

| Часть | Что внутри |
|---|---|
| ввод | события окна (`platform_poll`), размер окна |
| интерфейс | HUD, меню, панель отладки |
| шаги мира | 0..8 шагов за кадр с выпиской, записью повтора и хешем |
| вид | `view_build`: выписка → `RenderFrame` |
| ожидание GPU | `vkWaitForFences`: GPU доделывает кадр, который писал этот слот (2 кадра в полёте) |
| подготовка | пересоздание swapchain, сбор прошлого кадра (метки времени, счётчики), данные кадра в буферы |
| картинка | `vkAcquireNextImageKHR` |
| запись команд | граф кадра и запись команд |
| отправка | `vkQueueSubmit2` |
| показ | `vkQueuePresentKHR` |
| журнал | раз в секунду: заголовок окна и строки журнала (после этого PR — только копия в кольцо) |
| прочее | остаток: камера, намерения, сбор переполнений, снимки `--timelapse` |

Ожидание GPU, картинка и показ — время, когда процессор стоит. Если кадр упирается в GPU, время уходит в
«ожидание GPU»; с vsync — в «показ» или «картинку». Рывок, где растёт «ожидание GPU», а GPU (наибольший за
секунду) нет, — это очередь или драйвер, а не наши шейдеры.

Где видно:
- **F3, вкладка «Кадр»**: к/с, худший кадр, GPU среднее и худший за секунду; график последних 256 кадров (верх
  — ступень 1, 2, 4, 8, 16, 33… мс, линия на 16.7 мс; кадр вдвое длиннее среднего — ярче); таблица частей
  «среднее · наибольшее · в худшем кадре». `--open frame` открывает эту вкладку.
- **Журнал** раз в секунду: «кадр по частям, мс (среднее/наибольшее): …· худший N: три самые большие части».
- **Заголовок**: «GPU … мс (макс …)» — теперь среднее за секунду и худший, а не последний кадр.

«CPU кадра» в заголовке значит то же, что раньше: вид, подготовка, запись команд и отправка, без шагов мира и
без ожиданий.

## Кеш конвейеров
`vk_pipecache.cpp`. Все конвейеры создаются при запуске, поэтому кеш ускоряет запуск, а не кадр.
`pipelines.cache` рядом с игрой: свой заголовок (метка `APC1`, размер, хеш данных) и данные
`vkGetPipelineCacheData`. Файл читается до создания конвейеров и пишется сразу после, если данные изменились.
Драйверу отдаётся, только если совпали метка, размер, хеш и заголовок Vulkan (производитель, модель, UUID кеша
драйвера); иначе кеш пустой, а файл переписывается. С `--gpuav` кеш не читается и не пишется (шейдеры
дополнены проверками). Журнал при запуске: «кеш конвейеров: с диска / новый / другой драйвер…» и «конвейеры за
N мс».

Честно о пользе: драйвер NVIDIA и так держит свой кеш шейдеров на диске, поэтому на RTX повторные запуски
были быстрыми и без нашего кеша. Наш кеш даёт то же на любом драйвере и не зависит от того, где драйвер хранит
свой и когда его чистит. Рывков в кадре он не убирает: в кадре конвейеры не создаются. lavapipe кладёт в кеш
только заголовок (48 байт) и тратит ~20 с на конвейеры при каждом запуске.

## Чего нет
- **Ограничителя кадров нет** — решение пользователя (только vsync вкл/выкл, `docs/decisions.md`).
- Заголовок окна раз в секунду остаётся в потоке кадра (SDL требует окно из главного потока); его цена видна
  в части «журнал» (~0.2 мс на X11 в контейнере).
