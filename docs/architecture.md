# Архитектура: папки, модули, поток кадра

Это стартовая раскладка. Папка появляется, когда в ней появляется код, а не заранее.
Швы и запреты — в `docs/invariants.md`, они главнее этого файла.

## Папки

    Makefile
    src/platform/  окно, ввод, время, звук, файлы: platform.h, реализация на SDL3 (platform_sdl.cpp)
    src/core/      арены и пулы, RNG, математика, журнал, замер времени, сериализация
    src/asset/     чтение наших форматов: .mesh .skel .anim .spv .font (только чтение готового)
    src/render/    Vulkan: устройство, кадр, скиннинг, пост-обработка (пиксель, зерно, туман)
    src/anim/      скелет, выборка клипов, смешивание, root motion, IK стоп и рук, реакции
    src/sim/       мир боя: люди (SoA), опоры, действия, попадания по частям, шаг симуляции
    src/ai/        намерения: выбор цели, места вокруг цели, оценка действий (utility)
    src/view/      что видно: камера, сбор фигур кадра из состояния мира, интерполяция, HUD
    src/debug/     тестовые сцены, стенды, замеры, отладочное меню (без неё — NODEBUG=1)
    src/app/       main, цикл, сборка мира, режимы запуска (--bench, --shot, --replay)
    data/          готовые ассеты в наших форматах и описания (свой текстовый формат)
    tools/         конвертеры (humanconv, retarget, animconv, meshconv, fontconv, spv), run.sh, git-hooks
    third_party/   SDL3, Vulkan-Headers, volk, VMA, vk-bootstrap, QOA (+ Tracy, ImGui для отладки) с версиями
    docs/          что есть в игре и почему так

## Кто кого может включать
`platform` и `core` ни от кого не зависят. `asset` → core. `anim` → core, asset. `sim` → core, anim (только
данные клипов и выборка поз для попаданий). `ai` → core, sim (читает мир, пишет намерения). `render` → core,
asset, platform. `view` → всё выше, кроме ai. `app` и `debug` → всё. Проверка скриптом в CI (как `tools/layers.sh`
в складе) появляется на этапе 0.

## Поток кадра
1. `platform` собирает ввод за кадр.
2. Ввод игрока и `ai` превращаются в намерения.
3. `sim` делает 0..N фиксированных шагов: намерения → действия → движение по root motion → попадания →
   реакции. Состояние мира пишет только этот шаг.
4. `anim` считает позы людей рядом (пакетом, позже в потоках).
5. `view` собирает кадр из двух последних выписок с интерполяцией.
6. `render` рисует, `platform` показывает.

**Выписка для кадра.** В конце шага симуляция копирует то, что нужно кадру (положения, курсы, время клипов,
события шага), в выписку — кольцо из трёх. Кадр читает только выписки, не таблицы мира. Так перенос симуляции
в свой поток (`docs/stack.md`) ничего не меняет в `view`, а гонки за таблицы нет. С этапа 0, даже в одном потоке.

## Данные людей (набросок, уточнится на этапах 7–10)
Люди в структуре массивов на фиксированное число мест с поколениями (номер = место + поколение, как `Persons`
в складе). Группы столбцов: опора и положение относительно неё, курс; тело (части, раны); действие
(текущее, фаза, время); анимация (слои клипов и веса); внешность (тело, LOD, морфы).

## Модель симуляции (решено 2026-11-05, сверено с практиками Factorio, Bannerlord, RimWorld, Kenshi)
Образец — data-oriented design: данные в таблицах, код — функции над ними. Универсального ECS (EnTT, flecs,
архетипы) нет: видов сущностей мало (люди, отряды, вещи на земле, снаряды, постройки), поля известны заранее,
а порядок обхода должен быть явным ради повтора. Наследования сущностей (как у RimWorld) тоже нет.
- **Таблицы.** Один вид сущности — одна таблица SoA фиксированной ёмкости. Номер = место + поколение.
  Связи между сущностями — только номерами (указатели в состоянии мира запрещены: их не сохранить и не сравнить).
- **Системы.** Обычные функции `step_xxx(World&, StepCtx&)`. Порядок вызова — один список в `src/sim/step.cpp`.
  Над функцией строка: какие столбцы читает и какие пишет.
- **События шага** (начало действия, попадание, смерть) — в буферы шага, порядок по номеру сущности, а не по
  готовности. Их читают следующие системы того же шага, а после шага — вид и звук.
- **Память — три срока жизни.** Арена мира (таблицы, живут всю игру), арена шага (сбрасывается каждый шаг),
  арена кадра (вид и рендер). Загрузка и инструменты — своя арена.
- **Состояние мира = таблицы + RNG + номер шага**, больше ничего. Отсюда даром: сохранение — запись таблиц
  кусками, хеш шага — хеш таблиц, снимок для перемотки — копия таблиц.
- **Потоки.** Системы пишутся как обход таблицы кусками. `parallel_for` на пуле потоков с фиксированным разбиением,
  результаты складываются по номеру куска. Пул включаем, когда замер покажет нужду (этапы 12–13). Волокон (fibers)
  и графа задач нет.

## Повтор и проверка детерминизма (как у Factorio)
- Запись = версия + зерно + хеш описаний, которые читает шаг мира, + намерения игрока по шагам. Запуск с
  записью даёт тот же мир бит в бит. Горячая перезагрузка описаний пишется в запись как событие шага, иначе
  запись после неё не повторится.
- Эталонные хеши `--sim` лежат в файле в репозитории. Намеренная правка шага мира обновляет их отдельной
  командой, и это видно в диффе коммита.
- Хеш состояния: в отладке каждый шаг, в релизе раз в секунду, пишется в журнал. При расхождении двух прогонов
  `--replay` находит первый разошедшийся шаг и таблицу со столбцом.
- `--sim` — шаг мира без окна и GPU. CI гоняет на нём повтор и бенч и сравнивает хеши сборки Linux и Windows-exe
  под Wine с первого этапа: запреты по float проверяются сразу, а не когда бой уже написан.

## Отладка как часть каркаса
- Отладочное рисование (линии, капсулы, стрелки, текст в мире): симуляция пишет в буфер, рендер рисует. Прямых
  вызовов рендера из симуляции нет.
- Время: пауза, шаг по одному, замедление 0.1×–4× (меняется число шагов за кадр, не длина шага).
- Перемотка: кольцо снимков мира за последние ~10 с, ползунок в отладочном меню. Нужна для разбора удара по кадрам.
- Горячая перезагрузка описаний (действия, оружие) и шейдеров без перезапуска. Изменения ищутся опросом
  времени файлов (раз в ~0.5 с), а не уведомлениями ОС: Windows-exe читает файлы из WSL через `\\wsl$`, и
  уведомления оттуда не приходят. Старый конвейер шейдера живёт, пока его кадры не закончились.
